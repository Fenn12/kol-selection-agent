## 1. 背景与问题定义

### 1.1 现状痛点

达人投放运营每天被四类高频、低杠杆的工作占满：

| 痛点 | 具体表现 | 造成的损耗 |
|---|---|---|
| 线索散落在聊天里 | 达人自荐、MCN 报价、商务转发的账号 ID 混在企微群里，靠人工复制粘贴到表格 | 每条线索处理 3–5 分钟，一天 30 条即 2 小时；漏跟、重复跟进常见 |
| 选人靠"感觉" | "这个达人看起来挺匹配"没有统一口径，不同运营结论不一致，复盘时无法归因 | 投放 ROI 波动大，好经验沉淀不下来 |
| 内容复写与合规靠人工 | 同一篇卖点稿要改成小红书/抖音/视频号三种调性，还要逐条查极限词 | 一条稿 20–40 分钟；合规漏检直接导致下架或处罚 |
| 复盘与监测滞后 | 数据是看了，但"哪里异常、为什么异常、该动谁"要人工推断 | 异常往往在 3–5 天后才发现，预算已经烧完 |

### 1.2 为什么必须是 Agent，而不是网页或脚本

| 形态 | 能做 | 做不到 |
|---|---|---|
| 静态看板 / BI 报表 | 展示已有指标 | 不能判断"下一步该做什么" |
| 规则脚本 | 固定流程自动化 | 目标一变（"预算砍半" "换个品类"）就得改代码 |
| **Agent（本产品）** | 给定自然语言目标 → **自己写执行计划 → 选工具 → 看结果 → 发现不对就补查 → 自查数字来源 → 输出结论** | —— |

核心差别：**Agent 的中间步骤不是写死的，是模型根据工具返回的事实现场决定的。** 规则脚本只能回答预设问题；Agent 能回答"这波为什么没起量"这类开放问题。

### 1.3 一句话定义

> 面向达人投放运营的、以大模型为决策核心的 Agent：它接得住群里的线索，算得清达人的分，写得出能发的稿和话术，盯得住数据异常，并且**每一个数字都能回溯到工具返回**。

## 2. 目标与非目标

### 2.1 目标（Goals）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 把运营从"取数—粘贴—算分—写话术"的执行链条里解放出来 | 单个达人从线索到可用话术的耗时 ≤ 1 分钟（当前 3–5 分钟） |
| G2 | 选人判断标准化、可追溯、可归因 | 每个达人输出四维分 + 分层 + 评分依据字段，可导出审计 |
| G3 | 数据异常在当天被发现并给出归因方向 | P0 告警 T+0 触达，附"先查哪一环"的建议 |
| G4 | 内容产出合规可控 | 复写前后各跑一次合规检查，违规项数量必须在结论中显式对比 |
| G5 | 不增加运营的学习成本 | 非技术运营通过 Web 工作台零命令行完成全部操作 |

### 2.2 非目标（Non-Goals，明确不做）

| 不做 | 原因 |
|---|---|
| **自动向达人私信/批量触达** | 平台侧无稳定开放私信 API；批量私信触发风控；且无人确认的触达会伤害品牌形象。**改为：生成待发队列，人工一键复制后发送** |
| 替代星火 / 飞瓜 / 蝉妈妈等数据平台 | 它们没有免费公开 API。产品定位是**上层编排与决策**，数据平台仍由企业自行采购 |
| 自动抓取未经授权的聊天记录 | 企业微信群机器人的 Webhook 是**只发不收**；读取会话需企业管理员开通会话存档或自建应用回调。产品预留接入点，但**不绕过权限** |
| 让模型自行计算或修改数字 | 见 3.2「能算的用代码，要写的用模型」 |
| 全自动无人值守投放决策 | 高风险动作（预算分配、对外话术）一律标记需人工复核 |

## 3. 产品原则（设计约束，优先级高于功能）

### 3.1 五条硬原则

1. **先查数据，再下结论。** 涉及投放建议时，必须先调用销售/投放类工具。没查就说"一切正常"判为不合格。
2. **数字只能来自工具返回。** 禁止模型估算、禁止编造达人 ID 或报价。结论里的每个数字都要能对应到某次工具返回。
3. **不可行就直接说不可行。** 预算不足、候选池为空、数据缺失时，输出失败原因和建议动作，不硬凑一个看起来完整的方案。
4. **内容类产出双检。** 复写前跑一次合规检查，复写后再跑一次，两次结果都在结论里写明。
5. **人工终审不可跳过。** 对外发出去的 brief、话术、预算方案一律带"需人工复核"标记。

### 3.2 能算的用代码，要写的用模型

| 环节 | 实现方式 | 理由 |
|---|---|---|
| 评分、排序、ROI、预算分配、异常检测、漏斗归因 | **确定性 Python 代码** | 同样的输入必须得到同样的输出；需要能审计、能复现 |
| 商品简报、合作 brief、内容复写、邀约话术、日报结论 | **大模型生成** | 需要语义理解与表达，规则写不出可用的文案 |

**边界纪律：模型不得修改任何数字。** 模型负责"调用哪个工具、传什么参数、怎么组织结论"，数值一律由工具算出后原样进入结论。

### 3.3 监测基线用中位数，不用均值

异常期本身会把均值拉高，用均值做基线会导致"异常越严重越检测不出来"（实测中 K013 的曝光飙升就被均值基线吞掉）。因此滚动基线取**中位数**。

### 3.4 护栏分两级

| 级别 | 触发条件 | 行为 |
|---|---|---|
| **BLOCK** | 工具报错、候选池为空、预算不可行、销售数据为空、投放数据缺失 | 立即终止流程，输出原因 + 建议动作 |
| **WARN** | 合规未通过、产出属高风险类、本期零告警（阈值可能过宽） | 继续执行，但风险提示必须进最终结论 |

## 4. 用户与场景

### 4.1 角色画像

| 角色 | 诉求 | 使用方式 |
|---|---|---|
| 达人投放运营（主用户） | 快速选人、写 brief、盯数据 | Web 工作台 / 企微推送 |
| 内容运营 | 一稿多平台改写、过合规 | Web 工作台「内容复写」 |
| 投放负责人 | 看日报、看归因、做预算决策 | 日报 + 驾驶舱 |
| 数据分析 / BI（对接方） | 把企业库接进来 | `sql/mapping.json` 配置 |

### 4.2 五个核心场景（Job Stories）

**S1｜群里来了 30 条达人自荐**
> 运营把群消息贴进工作台 → Agent 抽账号 ID → 补全画像 → 四维打分分层 → 写入飞书多维表格 → 高分层达人自动生成货盘与邀约话术，运营逐条确认后发送。
> **验收**：30 条线索 ≤ 3 分钟完成入库与分层，零手工复制。

**S2｜指压板新品要起量，预算 8000**
> 运营输入目标 → Agent 先读销售结构（直播 52% / 客单价 23.3 元，置信度低）→ 推导打法 → 筛候选 → 四维评分 → 预算内选人 → 生成合作 brief 与议价要点。
> **验收**：输出 8 人名单、花费 690/8000，且明确给出客单价置信度低的提示。

**S3｜这波投放为什么没起量**
> Agent 按内容形式 / 达人两个维度复盘 ROI → 对最差的账号跑漏斗诊断 → 定位掉在曝光、点击率、转化率还是客单价 → 给出动作建议。
> **验收**：结论含整体 ROI、最好/最差分组、主因偏差百分比、建议动作。

**S4｜今天有没有异常账号**
> Agent 滚动比对近 3 天与近 7 天中位数基线 → 命中规则则产出 P0/P1 告警 → 对 P0 账号跑漏斗诊断。
> **验收**：4 条规则全覆盖，P0 才触发推送（避免告警疲劳）。

**S5｜给主管交日报**
> Agent 汇总监测告警 + 复盘结论 + 预算执行情况 → 生成 Markdown 日报 → 可一键推送企微/邮件。
> **验收**：日报含 P0/P1 计数、TOP 结论、待人工确认项，主管无需追问。

## 6. Agent 思考机制（本产品的核心，需求重点）

### 6.1 循环：Plan → Act → Observe → Repair → Reflect

```
      ┌──────────────────────────────────────────────┐
      │                                              │
  ① PLAN                                             │
     模型先写 3–6 步执行计划（含"还缺什么信息"）      │
     {"plan": [...], "missing": [...]}               │
     只输出计划，不给答案                             │
      ↓                                              │
  ② ACT                                              │
     模型带 14 个工具的 JSON Schema 发起 function     │
     calling，自行决定调哪个、传什么参数              │
      ↓                                              │
  ③ OBSERVE                                          │
     工具返回的事实作为 tool message 回灌进上下文     │
     （单条上限 6000 字符，防超窗）                   │
      ↓                                              │
  ④ REPAIR（条件触发）                                │
     参数不合法 → 把"可接受参数"回给模型，限改 1 次    │
     同轮未执行的并行调用补 skipped 回执（否则 API 400）│
      ↓                                              │
     回到 ②  ─────────────────────────────────────────┘
      ↓（模型不再调工具，准备作答）
  ⑤ REFLECT（一次性强制自检）
     "你结论里每个数字都能对上工具返回吗？
      有没有该查没查的？有没有该拒绝而你没拒绝的？"
     发现问题 → 回到 ② 继续调工具
     确认无误 → 输出最终答案
      ↓
  ⑥ FINAL
     判断依据（带数字）→ 结论/名单 → 风险与待人工确认项
```

### 6.2 思考机制的需求点

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-T1 | **先规划后执行** | 首次决策前必须先产出执行计划，`missing` 字段声明信息缺口；计划要展示给用户（Web 端「模型计划」卡片、CLI「执行计划」段） |
| FR-T2 | **自主工具选择** | 模型自行决定调用哪个工具、传什么参数，不做硬编码路由 |
| FR-T3 | **支持并行 tool_calls** | 模型一轮返回多个调用时，逐个执行并为每个 `tool_call_id` 补齐 tool 回执（OpenAI/DeepSeek 协议要求，缺失会报 400） |
| FR-T4 | **参数纠错** | 参数不合法时把可接受参数回灌，同一调用最多重试 1 次，避免死循环 |
| FR-T5 | **强制自检** | 模型准备作答时先注入自检提示，整个任务生命周期内触发一次；自检发现问题则继续调工具 |
| FR-T6 | **预算与步数双上限** | token 预算 80,000、规划步数上限 16、执行步数上限 40；触顶时明确声明"结论可能不完整" |
| FR-T7 | **思考过程可回放** | 每一步的 thought / tool / args / observation / 耗时 / 护栏标记写入 `traces/*.json`，可逐步骤回放 |
| FR-T8 | **降级不沉默** | 无 API Key 时自动回退规则规划器，并在 UI 与结论中显式标注当前用的是哪个规划器、模型是否可用 |
| FR-T9 | **用量可观测** | 记录调用次数、输入/输出 token、平均延迟，写入 `logs/llm_usage.jsonl` 并在接口与 UI 暴露 |

### 6.3 状态机

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| `PLANNING` | 任务开始 | 计划产出（或模型调用失败 → `FAILED`） |
| `ACTING` | 有工具可调用 | 无工具调用 → `REFLECTING`；触顶 → `FINAL` |
| `REPAIRING` | 参数不合法 | 重试 1 次 → `ACTING`；已重试过 → `ACTING`（跳过该调用） |
| `REFLECTING` | 模型准备作答且未自检过 | 补查 → `ACTING`；确认 → `FINAL` |
| `BLOCKED` | 命中 BLOCK 护栏 | 终止，输出原因 |
| `FINAL` | 自检通过 / 步数触顶 / 模型失败 | —— |
| `FAILED` | 模型调用异常 | 输出失败原因，不猜答案 |

### 6.4 与规则规划器的对照（为什么要保留 RulePlanner）

| 维度 | LLMPlanner | RulePlanner |
|---|---|---|
| 适用 | 有 API Key | 无 Key / CI 评测 / 离线演示 |
| 决策方式 | 模型现场决策 | 关键词路由（筛选/合作/复写/复盘/监测/日报） |
| 价值 | 处理开放问题 | **行为基线**：用固定序列验证工具链没坏，11 条评测跑的就是它 |
| 可解释性 | 输出计划 + 自检 | 每步附固定理由 |

保留规则规划器不是妥协，而是**让"模型有没有真的比规则做得好"变成可测量的**。

## 7. 功能需求

优先级：**P0 = 必须有，P1 = 应该有，P2 = 可以有**。

### 7.1 线索接入与达人识别（FR-1xx）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-101 | 从群消息文本中抽取小红书号 / 抖音号 / 账号 ID | P0 | 支持 `小红书号：xxx`、`抖音号：xxx`、`@handle`、纯 ID 多种写法 |
| FR-102 | 抗误抓：相邻数字不被误判为粉丝量 | P0 | `抖音号：jiuzuo2024 粉丝` 中的 `2024` 不得被识别为粉丝数；粉丝数 < 100 的候选丢弃 |
| FR-103 | 支持企微回调 payload 解析 | P1 | 能从 JSON 回调体中提取文本与发送者 |
| FR-104 | 去重与合并同一账号的多次提及 | P2 | 同 ID 只保留一条，记录出现次数 |

### 7.2 画像补全与风格拆解（FR-2xx）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-201 | 按账号 ID 拉取第三方指标（粉丝、互动率、爆文率、报价等） | P0 | 通过 `ThirdPartyClient` 适配器；**无公开 API 时以确定性 mock 兜底并标注来源** |
| FR-202 | 适配器可替换为企业已采购的数据源 | P0 | 换实现不动上层代码 |
| FR-203 | 拆解账号内容风格（选题偏好/表达调性/受众画像） | P1 | 输出结构化风格标签，供话术与 brief 使用 |
| FR-204 | 历史带货数据回捞（过往品类、GMV、履约率） | P1 | 进入四维评分的转化维与成本维 |

### 7.3 四维匹配模型（FR-3xx）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-301 | 四维加权评分：匹配 30% / 内容 25% / 转化 30% / 成本 15% | P0 | 与下表口径一致，权重可配置 |
| FR-302 | 维度内指标百分位归一化（批内相对排序，非绝对值） | P0 | 同一候选池内可比；换一批候选分数会变，需在 UI 注明 |

### 9.2 企业库参考表（`sql/schema_enterprise.sql`）

| 表 | 粒度 | 用途 |
|---|---|---|
| `product_sales_daily` | 商品 × 日 | 销售结构、客单价、达成率 |
| `dim_kol` | 达人 | 达人维表 |
| `fact_kol_daily` | 达人 × 日 | 投放监测与复盘 |
| `dim_content_sample` | 内容样本 | 内容复写与合规 |

### 9.3 区间值处理（重要）

平台导出普遍为区间值（`5000-1w`、`5%-10%`），必须：

1. `parse_range()` 统一解析为中值近似；
2. **派生指标要标注置信度**：客单价 = 销售额中值 ÷ 销量中值，两个区间相除会放大误差，置信度为「低」时需在结论中提示改用实际成交价；
3. 不得把区间中值当作精确数对外汇报。

## 14. 已知局限（不掩饰，写进 PRD）

1. **未配置 API Key 时不是 Agent**，是规则基线。产品在 UI 与结论中显式标注，不冒充。
2. **第三方数据为 mock**：星火/飞瓜无免费公开 API，未采购时画像指标来自确定性模拟，来源字段已标注。
3. **企微读取依赖管理员开通**：当前仅支持粘贴与回调体两种输入。
4. **评分为批内相对排序**：换一批候选，同一个人分数会变，UI 已注明。
5. **客单价为区间派生**：置信度低时需改用实际成交价。
6. **自动私信不做**：能力、合规、效果三方面都不成立，改为人工确认的待发队列。
