## 1. 五分钟跑起来

**需要什么**：Python 3.9+。不需要 Node、不需要数据库、不需要 API key。

```bash
git clone https://github.com/Fenn12/kol-selection-agent.git
cd kol-selection-agent
python web/server.py
```

浏览器打开 **http://127.0.0.1:8765**，能出数据就说明通了。

不想开界面，用命令行：

```bash
python run_agent.py --goal "指压板新品起量，预算 8000"
python eval/run_eval.py          # 自检：应输出 11/11
```

**如果报错**：

| 报错 | 原因 | 处理 |
|---|---|---|
| `ModuleNotFoundError: agent` | 不在仓库根目录 | `cd` 到有 `run_agent.py` 的那层 |
| 端口被占用 | 8765 已有人用 | `PORT=8800 python web/server.py` |
| 页面空白 | 静态文件没加载 | 确认 `web/static/` 下三个文件都在 |

**想接大模型**（可选，不接也能用全流程，但就不是 Agent 而是规则基线了 —— 见第 2 节）：

```bash
cp .env.example .env     # 然后填 DEEPSEEK_API_KEY=sk-xxx
```

## 2. 接模型：让它真的会思考

不接模型时，本仓库跑的是 **RulePlanner**：按关键词路由到固定工具序列。功能不缺，但它是**规则脚本**，不是 Agent —— 目标一变就得改代码。

接了模型才启用 **LLMPlanner**，也就是产品文档里定义的那套思考闭环。

### 2.1 两种配法

```bash
# 方式一：.env（推荐）。已加入 .gitignore，不会误提交
cp .env.example .env
# 编辑：
#   DEEPSEEK_API_KEY=sk-xxx
#   DEEPSEEK_BASE_URL=https://api.deepseek.com/v1   # 可选
#   MODEL=deepseek-chat                             # 可选

# 方式二：环境变量
export DEEPSEEK_API_KEY=sk-xxx
```

`.env` 的加载规则是**只补不覆盖**：已经存在的环境变量优先。这样 CI 里注入的 key 不会被仓库里的文件顶掉。

任一 OpenAI 兼容接口都行（DeepSeek / 通义 /  moonshot / 本地 vLLM），改 `DEEPSEEK_BASE_URL` 与 `MODEL` 即可。

### 2.2 验证连通性

```bash
# 方式一：Web 工作台顶部「测试 AI 连接」按钮
python web/server.py

# 方式二：命令行
curl -X POST http://127.0.0.1:8765/api/llm/test
curl http://127.0.0.1:8765/api/llm/status
```

`/api/llm/status` 返回示例：

```json
{"available": true, "model": "deepseek-chat", "base_url": "https://api.deepseek.com/v1",
 "env_file": true, "env_loaded": 3,
 "usage": {"calls": 42, "prompt_tokens": 142195, "completion_tokens": 7815, "avg_latency_ms": 1787}}
```

未配 key 时 `/api/llm/test` 返回 400 并明确提示「未配置 DEEPSEEK_API_KEY（可写入项目根目录 .env）」，不会假装成功。

### 2.3 思考闭环长什么样

```
① PLAN     先写 3–6 步执行计划，声明「还缺什么信息」——只给计划，不给答案
② ACT      带 14 个工具的 JSON Schema 做 function calling，自己选工具、自己传参数
③ OBSERVE  工具返回回灌上下文（单条截断 2400 字符）
④ REPAIR   参数不合法 → 回灌可接受参数，同一调用只重试一次
⑤ REFLECT  准备作答时强制自检一次：
            «每个数字都对得上工具返回吗？有没有该查没查的？有没有该拒绝而你没拒绝的？»
            → 有问题就回去补查，没问题才输出
⑥ FINAL    判断依据（带数字）→ 结论/名单 → 风险与待人工确认项
```

跑一次，执行计划会直接打印出来：

```bash
python run_agent.py --goal "指压板新品起量，预算 8000，帮我选人并给出合作建议" --planner llm
```

```
执行计划
  1. 用 parse_product_sales 拉取销售与转化数据，明确客单价、人群与起量目标
  2. 用 build_brief 生成选人 brief，再用 search_candidates 检索候选池
  3. 用 score_candidates 打分排序，产出优先名单与分层
  4. 用 allocate_budget 在 8000 预算内做组合分配
  5. 用 draft_collab_brief 与 negotiation_advice 输出合作 brief 与议价要点
  6. 用 draft_outreach_message 生成触达话术，汇总为可执行建议
```

### 2.4 一次真实运行里，自检抓到了什么

第 9 步，模型自己列出的三个问题（原文摘自 trace）：

> 1. **数字溯源**：「差 5–7 倍」是我自己算的派生值（130/23.3、170/23.3），不是工具返回，需标注。
> 2. **该查没查**：用户要「起量」，我给了名单却**没跑 monitor_scan、没跑 review_campaign**，这两项直接影响预算该集中还是分散。
> 3. **该拒绝没拒绝**：`allocate_budget` 已提示「预算只用掉 8%、池子已选完」，我不该仍然输出看似完整的方案，**正确做法是先扩池，或明确拒绝**。

然后它自己回头补调了 `review_campaign` 与 `monitor_scan`，重跑评分与分配，最后给出结论：

> **结论：这不是一个 8000 元的完整方案** —— 首批 4 人合计 760 元（占预算 9.5%），剩余 5390 元是硬缺口，我不硬凑。
> 风险：打法与候选池不匹配——销售结构显示直播占 51.7%，但候选池**无直播达人**；客单价 23.3 元置信度低，ROI 无法可靠测算。
> 未跑监测/复盘：不是「一切正常」，是**尚无数据可判**。

**这类行为不是规则写出来的**，是模型按 system prompt 里五条硬原则现场判断的。这正是本产品与「网页 + 几个接口」的区别。

### 2.5 可调参数

| 参数 | 默认 | 位置 | 说明 |
|---|---|---|---|
| 规划步数上限 | 16 | `LLMPlanner(max_steps=)` | 不含并行调用展开的步数 |
| token 预算 | 150,000 | `LLMPlanner(token_budget=)` | 触顶时强制收尾并说明不完整 |
| 单条观察上限 | 2,400 字符 | `LLMPlanner(obs_limit=)` | 调大更准、更贵；调小更省、可能漏信息 |
| 上下文压缩阈值 | 40,000 字符 | `LLMPlanner(ctx_chars=)` | 超阈值后更早的 tool 回执压成摘要，最近 8 条保留完整 |
| 执行步数上限 | 40 | `runner.Agent.run(max_steps=)` | 含并行调用展开后的总步数 |
| 温度 | 0.2 | `planner.py` 各次调用 | 选人/算分类任务不建议调高 |

**成本参考**：一次完整选人任务约 40 次模型调用、14 万输入 token、30–40 秒。按 DeepSeek 官方价约几毛钱一次。记账在 `logs/llm_usage.jsonl`。

### 2.6 与规则规划器做对照

```bash
python eval/run_eval.py --planner rule    # 离线基线：11/11
python eval/run_eval.py --planner llm     # 接模型后跑同一批断言，做对照
```

保留规则规划器不是妥协。它让「模型到底有没有比规则做得好」变成可测量的，而不是一句宣传。

## 3. Web 工作台怎么用

界面分四块，从上到下就是每天的动线。

### 左侧栏：常用指令

五个按钮，点一下就跑：

| 按钮 | 内部走什么 | 什么时候用 |
|---|---|---|
| 选人排期 | 解析商品 → 简报 → 检索 → 评分 → 预算分配 | 要定这波投谁 |
| 投放复盘 | 按内容类型/达人聚合 ROI | 周会前看效果 |
| 异常监测 | 近 3 天 vs 前 7 天比对 | 每天早上扫一眼 |
| 内容复写 | 合规检查 → 改写 → 再检查 | 收到的达人稿要改 |
| 全流程 | 五类能力串跑 | 想一次看全貌 |

预算输入框会影响选人与日报口径。规划器三选一：**自动**（有 key 用模型）、**离线规则**（稳定可复现）、**大模型规划**（强制走模型）。

### 驾驶舱：一屏判断今天要不要动手

四张卡：**待处理告警**（P0/P1 分开）、**整体 ROI**、**最优内容类型**、**估算客单价**。

客单价卡片会带**置信度**。这是因为客单价由「销售额区间中值 ÷ 销量区间中值」得来，两个区间相除会放大误差——置信度低时卡片上会直接写「不用于硬筛选」，避免有人拿 23.3 元去定价格带。

### 今日待办

不是罗列数字，每条都带「查什么」：

```
[P0] K040 转化骤降 -64.8%  → 素材衰减或落地页异常，先停投再排查
[P0] K013 曝光异常飙升 +58.7% → 曝光涨但转化没涨，注意流量错配
```

### 线索池：从群消息到名单

粘贴一段企微群消息，点「解析并入库」。它会抽账号 → 补画像 → 四维评分 → 写表 → 给高匹配的产生货盘和话术。

详细说明见 [第 4 节](#4-线索流水线群消息--达人名单)。

## 4. 五个能力分别怎么用

### A. 达人筛选

**输入**：商品销售分布（区间值也行）+ 候选池 + 预算
**输出**：S/A/B/C 分层名单，含匹配分与入选理由

```bash
python run_agent.py --goal "指压板新品起量，预算 8000"
```

评分四维：匹配度 30 / 内容 25 / 转化 30 / 成本 15。成本只占 15%，因为**成本是筛选条件，不是决策依据**——权重给太高会系统性偏向「便宜但没效果」的号。

### B. 合作 brief 与报价谈判

名单出来后在界面上点对应达人的 `Brief` 按钮，会把完整 brief 复制到剪贴板：
必现要素、禁止事项、交付要求、建议压价区间（75–95 折，留谈判空间）。

谈判建议会对比**同池 CPM 中位数**：报价高于中位 35% 以上判「偏高，建议压价或换人」；低于 25% 判「显著偏低，注意履约质量」。

### C. 内容复写

输入一条不合格的稿子，输出可投放版本。流程是**先查、再改、再查**，两次合规结果都报：

```
违规 3 → 0　｜　小红书 300–500 字目标
改动：删除医疗功效；去掉泛开场；硬引导改软引导
```

平台字数不同：小红书 300–500、抖音 80–150、视频号 120–200。

### D. 数据复盘

按内容类型 / 达人层级 / 单达人三个维度聚合 ROI、CTR、CVR、CPM。

单达人还能做**漏斗诊断**，把变化拆到曝光 / 点击率 / 转化率 / 客单价四环，指出主因：

```
K040：转化率 -50.1%，曝光 +11.3%，点击率 +1.6%
→ 主因「转化率」，查详情页、价格、评价；加投只会烧钱
```

### E. 邀约与日报

**邀约**：名单每行 `邀约` 按钮，一键复制首次触达话术（提到对方具体内容方向、说清预算区间、低门槛下一步、附发送前确认项）。

**日报**：右上角「生成日报」，产出给主管看的一页纸——整体数据、要动的告警、建议动作、需人工确认项。

## 5. 线索流水线：群消息 → 达人名单

这是最接近真实工作流的一段：运营在群里丢一个账号，系统自动补全、评分、入库、配话术。

### 怎么用

**方式一：界面粘贴**（推荐先试这个）

左侧「线索池」→ 粘贴 → 解析并入库。支持的内容形态：

```
抖音号：jiuzuo2024 粉丝 12.3w，做久坐缓解的
小红书号：aijiankang_xhs  主页 https://www.xiaohongshu.com/user/profile/5f8a2b1c
v.douyin.com/iRxT9kQ  粉丝4.5万
```

识别规则（`agent/integrations.py` 的 `PATTERNS`）：
`小红书号：xxx`、`抖音号：xxx`、`xiaohongshu.com/user/profile/xxx`、`v.douyin.com/xxx`、`xhslink.com/xxx`。

**抽不到就返回空**，不做猜测——猜错的成本比漏掉高。

**方式二：接口调用**

```bash
curl -X POST http://127.0.0.1:8765/api/pipeline \
  -H "Content-Type: application/json" \
  -d '{"text":"抖音号：jiuzuo2024 粉丝 12.3w","write":true,"push":false}'
```

**方式三：命令行**

```bash
python -c "
from agent import pipeline
r = pipeline.run_pipeline(['抖音号：jiuzuo2024 粉丝 12.3w'])
print(r['leads'])
"
```

### 产出什么

| 字段 | 来源 | 说明 |
|---|---|---|
| 平台 / 账号ID | 消息正则抽取 | 抽不到就是空，不猜 |
| 昵称 / 内容方向 / 风格 | 星火·飞瓜（或 mock） | 未配凭证时按账号 ID 稳定生成 |
| 粉丝 / 近30天曝光 / 客单价 / 报价 | 同上 | 用于四维评分 |
| 匹配分 / 分层 | 本地四维模型 | **代码算，模型不能改** |
| 风格拆解 | 规则 + 画像 | 一句话说清「他能怎么用」 |
| 建议动作 | 分层映射 | S 立即发货盘／A 进邀约队列／B 先寄样／C 留档 |
| 话术状态 | 是否高匹配 | 只有 S/A 生成 |

### 风格拆解为什么重要

不同风格的达人，投放方式完全不同。系统给的拆解会带具体建议：

- **实测型** → 讲「用了一周的真实感受」，不适合参数堆砌
- **测评对比型** → 适合打「同价位怎么选」，注意别引导贬损竞品
- **生活vlog型** → 把产品放进日常动线，转化靠氛围不靠卖点
- **知识科普型** → 讲原理清晰，注意避开医疗表述
- **种草型** → 短期起量快，但复购与客单偏低，适合入门款

## 7. 接企业微信

### 先说清楚能做和不能做的

| 想做 | 能不能 | 说明 |
|---|---|---|
| 往群里推消息 | ✅ 能 | 群机器人 webhook，5 分钟配好 |
| 读群聊天记录 | ⚠️ 有条件 | 见下方三条路 |
| 自动私信陌生达人 | ❌ 不能 | 企微没有这个开放能力，也不建议做 |

**读聊天记录的三条路**：

1. **群机器人转发**（最轻）：在群里用「消息转发/收集」类小工具，把候选账号消息转给本服务。不需要管理员权限。
2. **自建应用 + 消息回调**（标准做法）：企业管理员创建自建应用，配置回调地址指向本服务的 `/api/pipeline`。**回调地址必须公网可达**（内网需反向代理）。
3. **会话内容存档**（最全但最重）：需企业开通存档、通过服务商 SDK、拿到私钥解密。适合已经有合规存档的团队。

三条路都需要企业管理员配合，**不是技术侧单方面能搞定的**。这也是本仓库默认提供「粘贴导入」的原因——先把链路跑通，再补数据通道。

### 配置群机器人推送

1. 企微群 → 右上角 → 群机器人 → 添加 → 复制 Webhook 地址
2. 配进环境变量：

```bash
export WECOM_BOT_WEBHOOK="https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx"
```

3. 验证：

```bash
python -c "
from agent import integrations
print(integrations.wecom_send('测试：线索流水线已接通'))
"
```

未配置时不会报错，消息落到 `outbox/wecom_outbox.jsonl`，链路照样能验证。

### 回调接入（如果你选了路 2）

把企微回调地址指向：

```
POST https://你的域名/api/pipeline
```

请求体兼容三种形态：`{"text":{"content":"..."}}`、`{"content":"..."}`、`{"messages":[...]}`。

**注意**：企微回调需要做 URL 验证（echostr）与消息解密，这部分要按官方文档在你的网关层处理。本服务只负责「拿到明文文本之后」的部分。

## 8. 接星火 / 飞瓜

两家都**没有免费公开 API**：飞瓜有开放平台（需商务开通），星火（新红）同理。所以代码里做了一个可替换的客户端：

```python
# agent/integrations.py
class ThirdPartyClient:
    def profile(self, platform, account_id): ...
```

**未配置时**：用账号 ID 的哈希做种子生成稳定的假数据，字段结构与真实接口对齐，用于打通链路。每次跑同一个账号结果一致，可复现。

**要接真实接口**：

```bash
export KOL_TP_PROVIDER=feigua
export KOL_TP_BASE=https://your-gateway/feigua
export KOL_TP_TOKEN=xxx
```

然后按对方的返回结构，在 `_remote()` 里做一次字段映射（大约 20 行）。约定见下表：

| 字段 | 含义 | 示例 |
|---|---|---|
| `followers` | 粉丝数 | `123000` |
| `category` | 内容方向 | `运动健身` |
| `style` | 内容风格 | `实测型` |
| `price_band` | 粉丝消费力档位 | `中客单` |
| `engagement_rate` | 互动率（小数） | `0.045` |
| `viral_rate` | 近30天爆文率（小数） | `0.18` |

## 10. 高匹配自动发货盘与话术

### 触发条件

分层 **S 或 A**（匹配分 ≥ 62）。B 只建议寄样，C 不生成。

### 产出

每条高匹配线索会生成：

- **货盘**：3 个 SKU，含售价与佣金率
  ```
  指压板·小号  ¥39 / 20%  入门款，适合新手试水
  指压板·大号  ¥59 / 22%  主力款，客单与转化最平衡
  指压板+收纳袋 ¥89 / 25%  礼盒装，适合节日/送长辈
  ```
- **话术**：先体现了解对方内容 → 给三个价位 → 低门槛下一步（寄样）
- **发送前确认**：垂类是否变了、佣金结算口径、首次触达别附链接

### 为什么默认不自动发送

产品上做成「生成待发队列 + 一键复制」，而不是全自动私信，有三个原因：

1. **能力上做不到**：企微没有开放「私信陌生人」的接口，硬做只能靠灰产工具，账号有风险。
2. **合规上不该做**：未经同意批量触达属于骚扰，平台侧会限流甚至封号。
3. **效果上不划算**：达人商务的核心是「让他觉得你懂他」，模板化群发的回复率极低，反而不如人工发 10 条。

所以流程是：**系统准备好 90% 的内容，人做最后的判断与点击**。这才是提效，而不是替代判断。

如果确实要批量推，建议推给**运营群**（`WECOM_BOT_WEBHOOK`），由人分派，而不是直接发给达人。

## 12. 常见问题

**Q：一定要配大模型吗？**
功能上不用——所有能力都有离线实现（规则 + 模板），11 条行为评测在离线状态下全过。但**不配模型时跑的是 RulePlanner（规则脚本），不是 Agent**：工具序列是按关键词路由的固定流程，目标一变就得改代码。要「会思考」必须配 key，见第 2 节。UI 顶部会明确写当前用的是哪个。

**Q：数据会被传到哪？**
配置了模型才会把 prompt 发到模型服务商；数据源、飞书、企微都是你自己配的地址。默认不向任何第三方发送业务数据。

**Q：能改成别的品类吗？**
能，但要重标三样东西：监测阈值、价格带分档、禁用词清单。评分四维是通用的。这三样都放在常量里，改起来不用碰逻辑。

**Q：为什么监测用中位数不用均值？**
异常期会被算进基线，均值会被自己稀释。实测中同一份数据，均值基线漏掉了「曝光 +58.7% 但转化 −56%」这个组合，改中位数后命中。

**Q：11/11 是不是说明模型效果好？**
不是。那是**行为断言**通过率——测的是「预算不足会不会拒绝」「没数据会不会停」「工具顺序对不对」。模型效果不在这个数字里。

**Q：数据量大了会慢吗？**
当前所有查询都是单表 SELECT，无 JOIN。真正的瓶颈在第三方接口调用频率，建议加本地缓存（`agent/datasource.py` 里预留了位置）。

**Q：一次任务花多少 token？**
典型选人任务约 40 次调用、14 万输入 token、30–40 秒。记账在 `logs/llm_usage.jsonl`，实时看 `GET /api/llm/status`。嫌贵就调小 `LLMPlanner(obs_limit=)`（默认 2400 字符），代价是回灌给模型的事实更少。

**Q：为什么有时结论里写「已达上限，以下可能不完整」？**
步数（16）或 token（150,000）触顶了。触顶时不会丢一句占位话，而是再问模型一次让它基于已有事实把结论说完，并声明哪里不完整。长任务建议把目标拆细，或调大 `token_budget`。

**Q：模型会不会自己编数字？**
设计上不允许：SYSTEM prompt 写明「数字只能来自工具返回，禁止估算、禁止编造达人 id 或报价」，REFLECT 阶段还会逐条自查数字溯源。评分、ROI、预算分配本身由代码算，模型改不了。**但不等于零风险**——涉及金额的方案仍需人工复核，这也是所有高风险工具都进 WARN 的原因。
